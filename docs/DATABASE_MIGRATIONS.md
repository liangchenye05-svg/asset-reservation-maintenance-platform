# Flyway V1/V2/V3与安全迁移

| 版本 | 内容 |
| --- | --- |
| V1 | users、device、reservation、repair_order原四表结构，无账号或业务种子数据 |
| V2 | repair_order_history、维修前状态快照、预约/维修查询索引 |
| V3 | 持久历史完整性、设备恢复暂停、真实核对说明；不补造旧事件 |

## 新空演示库

在操作者控制的全新空库中使用安全示例与FLYWAY_ENABLED=true，按V1→V2→V3执行。应用不自动创建数据库，也不创建默认ADMIN。库已存在时先核对，禁止删库重建或盲目复用。

schema.sql提供当前V3空库兼容结构，主要供原测试初始化；不要与Flyway在同一库重复初始化。已发布V1/V2/V3不得随意编辑，后续结构变化增加新版本。

## 已有数据环境

先明确目标、版本/校验和、结构/索引/外键、触发器/例程及旧数据，再停全部旧写入、做完整私有备份，并在全新隔离恢复库验证结构与内容指纹。没有Flyway的旧V1库只有结构精确匹配且经明确批准后才能baseline为1；baseline不是执行过V1的证据，不启用自动baseline接管未知库。

已有V2先审查V3三列冲突及旧PROCESSING/快照/受理历史。V3默认旧工单不完整，仅完整有序真实链可标完整；缺快照或受理依据的设备暂停恢复。保留原字段、时间与历史，不通过造用户、改预约或补历史使验收通过。

显式迁移后先核对旧列指纹/行数、状态/时间/历史、Flyway成功记录/checksum、新列定义及分类，再切新版。正常重复启动应不重复迁移，但不能用普通应用启动替代受控接入流程。新版依赖V3，旧新服务不安全混跑。

MySQL DDL可隐式提交，失败不能假设整体rollback。保持停写、保留现场，核对已完成对象和Flyway状态，另行制定修复；不自动clean/repair/drop列/重建库或用备份直接覆盖真实数据。应用回退也不能让旧服务绕过人工核对保护。

公开仓库不包含真实库备份、业务数据、密码散列、操作日志或日常配置。合成测试的迁移/回滚不等于可无条件恢复任意真实数据库。
