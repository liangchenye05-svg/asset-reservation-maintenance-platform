# 设备协作台：接口与前端使用说明

本次增加的是现有 Spring Boot 项目内的演示前端，HTML/CSS/JavaScript 直接由后端提供，不需要另装 Node、npm 或启动前端服务。页面使用真实接口，没有浏览器内模拟业务数据。

## 启动

按 README 配好 MySQL 和本机运行环境，在 IntelliJ IDEA 中运行 `EquipmentManagementApplication`，或在项目根目录运行：

```powershell
.\mvnw.cmd spring-boot:run '-Dspring-boot.run.arguments=--server.address=127.0.0.1'
```

启动后在浏览器打开 <http://127.0.0.1:8080/>；页面与后端使用同一地址。端口如果在本地配置中修改，请使用实际端口。页面不能通过双击 index.html 正确使用，需要通过后端地址访问。

数据库、JWT 密钥仍使用项目原来的配置机制。本次没有修改本地口令、自动升级账户权限或初始化业务数据。正式项目使用你自己的已注册账号；新账号默认为 USER。管理员按 README 的已有流程，由项目负责人对明确的专用账号配置 ADMIN 权限。没有内置共享管理员和密码。

## 页面与操作

| 页面 | 普通用户 | 管理员 |
|---|---|---|
| 登录／注册 | 注册 USER、登录、退出 | 使用已有 ADMIN 账号登录 |
| 设备资源 | 分页浏览、发起预约、提交报修 | 另外支持新增与编辑设备 |
| 预约记录 | 仅本人预约，按状态筛选、分页、详情和可取消时段内取消 | 查看全部预约，详情、取消 |
| 维修工单 | 仅本人报修及处理状态 | 全部工单、受理、完成 |
| 审批工作台 | 不显示 | 待审批预约、批准、拒绝、待处理维修与数量统计 |

统计值读取接口；不是固定演示数字。设备名称在已加载设备中映射，找不到时显示设备ID，保证不会把未知ID显示成别的设备。维修页面选择 PENDING、PROCESSING、COMPLETED 时调用 `GET /repair-orders?status=对应状态`，选择全部时调用不带参数的 `GET /repair-orders`。列表和数量直接使用后端响应，不再重复进行浏览器端状态过滤。身份及数据范围仍由 JWT 和后端权限控制。当前没有服务端分页或设备筛选，记录量较大时可后续扩展。

JWT 保存在当前标签页的 sessionStorage，退出或收到已登录状态下的401后清除；它不是服务端主动撤销Token的退出功能。用户角色通过 `/users/me` 读取，前端按钮仅为操作引导，权限仍由后端验证。接口错误会在表单中显示，提交时禁用按钮；写请求超时后提示先刷新核对结果，避免重复提交。

## 本次接口变化

### 创建预约（已有接口的返回契约变化）

`POST /reservations`

请求字段：`deviceId`、`startTime`、`endTime`。用户身份取当前认证主体，客户端的 userId、status、id 等字段不用于创建。

```json
{"deviceId":1,"startTime":"2030-01-02T09:00:00","endTime":"2030-01-02T10:00:00"}
```

成功从原来的 **200 + 整数1** 改为 **201 Created + 保存后的预约对象**，并包含 `Location: /reservations/{id}`。

```json
{"id":42,"deviceId":1,"userId":7,"startTime":"2030-01-02T09:00:00","endTime":"2030-01-02T10:00:00","status":"PENDING","createdAt":"2030-01-01T10:00:00"}
```

以上ID和时间只是结构示例。数据库生成ID并回读记录，前端可以直接展示编号和调用详情。已有 Apifox、脚本或调用方中对200／整数1的断言，需要改为201／响应JSON中的id。前端实现阶段已同步两组相关测试；外部请求集合未自动重写。本轮公开内容准备没有再改测试代码。

### 预约列表

`GET /reservations`，别名 `GET /reservations/page`。

参数：`page=1`、`pageSize=10`（1～100）、可选 `status`、可选正整数 `deviceId`。状态支持 PENDING、APPROVED、REJECTED、CANCELLED；空状态表示不筛选。按ID倒序，返回 `{total,page,pageSize,records}`。

USER 的记录与总数均限制为本人；ADMIN 查看全部。客户端传 userId 不会扩大访问范围。过滤使用参数绑定SQL。页码、单页数量、状态和设备ID不合法返回400。

### 预约详情

`GET /reservations/{id}`：本人或 ADMIN 可读；其他用户403；不存在404；非正整数ID为400；未登录401。

### 当前用户

`GET /users/me`：返回 `{id,username,role}`，不返回密码、密码散列或JWT。

### 维修工单状态筛选

`GET /repair-orders` 支持可选 `status`：`PENDING`、`PROCESSING`、`COMPLETED`。省略时保留原数组契约及身份范围；合法状态无匹配记录返回 HTTP 200 和 `[]`。未知值、小写、空字符串和空白值返回 HTTP 400，正文“状态不合法”。USER 只能查本人，ADMIN 可查全部，均按 ID 倒序。

这是后端接口能力。当前页面仍拉取无状态参数的列表后在浏览器内筛选，不宣称已接入后端筛选，也没有工单服务端分页。

### 原有业务接口

预约批准、拒绝、取消，工单创建、受理、完成等业务规则继续使用原实现；这些写接口仍返回原来的整数1。页面公开访问只允许GET访问首页及静态资源，不放开业务数据接口。没有增加宽泛跨域配置，也没有更改数据库表结构。

## 演示顺序

1. 普通用户在设备页创建两个重叠时段的待审批预约。
2. 管理员进入审批工作台批准其中一个；批准另一个时看到后端返回的冲突提示，再拒绝第二个。
3. 普通用户查看状态和详情，取消尚未开始的已批准预约。
4. 普通用户提交报修，管理员受理、完成，普通用户查看已完成状态。
5. 使用另一个普通账号查看预约／工单，应只显示自己的记录。

维修设备与预约的进一步联动规则不在本次范围：页面不会承诺“维修中禁止预约”或“维修完成自动恢复设备台账状态”。这与现有后端行为一致。
